Personal Product Watch

Purpose

I’m building a product watcher that checks offers against product requirements, a preferred unit price and a maximum unit price.

Approach

I use TypeScript, Cloudflare Workers and D1, with separate workflows for checking offers and sending email alerts.

Status

Personal project · Live application for my own use, plus a public demo with fictional data. Private repository.

Try the public demo ↗(opens in a new tab)
  • TypeScript
  • Cloudflare Workers
  • D1
  • SQLite
  • GitHub Actions

Criteria and fair comparison

A watch describes the product requirements and price limits, rather than relying on a single listing URL. For instance, detergent prices are compared per wash, so different pack sizes can be assessed against the same limits. Product variants and missing information also affect whether an offer qualifies.

Checking and alerting

The private application stores the requirements for each watch and supports manual and scheduled checks. It prepares email alerts for offers that meet those requirements. The application runs on Cloudflare Workers with D1 storage, and GitHub Actions runs the checking workflows.

A public demo with clear boundaries

Visitors can adjust sample limits, compare fictional offers and preview an alert without signing in. The demo does not search retailers, make purchases or send email. The live application is for my own use.

Registration and administration

I’m developing the Angular front end and Spring Boot REST API. Players can register and edit their profiles; administrators can search member records and manage teams.

Registration checks and email

Registration checks for duplicate accounts and records an audit trail. Notification emails are sent after the database transaction commits, so a rolled-back registration does not trigger an email.

HomeWizard Energy Intelligence

Purpose

I’m building an application to collect smart-meter readings and review energy history. It also supports load-shifting scenarios: moving electricity use to a different time.

Approach

I save readings locally before upload, support retries and make missing readings visible in the history.

Status

Personal project · Private hosted application. Tariff, solar, battery and cost comparisons are in development.

  • Java
  • React
  • SQLite
  • Supabase
  • Local storage, upload retries, and replay
  • Historical imports and data-coverage checks
  • Recorded readings kept separate from estimates

Collection and recovery

The Java collector reads the HomeWizard API and saves readings in SQLite before uploading them to Supabase. Failed uploads can be replayed without creating duplicate records.

Energy history

The React and TypeScript interface requires sign-in and uses Supabase data. It shows the reading history, where data is missing and how recent the readings are. That way, gaps remain visible when reviewing energy use.

Development status

The application is hosted privately and supports energy-history exploration and load-shifting scenarios. Tariff, solar, battery and cost comparisons are still in development.
